## 슬라이드 (8장 · 각 30~45초)

### 1. 문제 (0:00–0:40)
- AI에게 "이 조건으로 사줘"라고 맡기면 **결제 기록만으론 "누가 얼마까지 어디서 사라 했는지" 재구성이 안 된다.**
- 위험 7가지 중 핵심: 수수료 빠뜨린 예산 초과 · 미등록 판매자 결제 · 기한 지난 실행 · 중복 지출.
- **한 줄:** "AI가 돈을 쓴 뒤, 그게 내 허락 범위였는지 아무도 증명 못 한다."

### 2. 해결 — 한 문장 (0:40–1:10)
> AgentGuard는 AI 에이전트의 결제 요청을 **사용자 정책으로 코드가 검사·차단**하고, 지시→승인→거래를 **검증 가능한 기록**으로 잇습니다.
- 세 주체의 분리: **AI = 초안 / 코드 = 판정 / 사람 = 승인.**

### 3. 핵심 설계 — 경계는 코드가 강제한다 (1:10–1:50)
- 정책 엔진(`packages/policy`)이 **판매자·품목·금액·수수료·기한·누적예산**을 결정론적으로 검사.
- AI 추론이 규칙을 우회할 수 없다. 경계는 코드에 있고, 그래서 재현 가능하다.
- 긴급 **중지(stop)** 시 허용 범위 요청도 차단 → 로그로 검증.

### 4. 라이브 데모 — 게이밍 모니터 8단계 (1:50–3:00) ★ 핵심
데모 전 **초기화 버튼** 필수. 사전 점검은 `node --env-file=.env scripts/rehearse-demo.mjs --reset` (8단계 자동 검증, 끝나고 다시 초기화).
1. `승인된 판매자에서 게이밍 모니터를 30만원 이내로 구매해.` → Qwen이 초안(300,000원·gaming_monitor·DisplayHub/TechStore). **말하지 않은 자동승인 한도·기한은 확인 질문으로 남는다.**
2. 사람이 자동승인 270,000원·기한 입력 후 적용 → 새 정책 버전.
3. 299,000원 모니터 → **승인 대기**(예약 299,000) → 4. 사람이 **거절** → 예약 해제.
5. 미등록 판매자 219,000원 → **차단**(merchant_not_allowed).
6. 249,000원 → **자동 승인**(지출 249,000).
7. 같은 상품 + 수수료 60,000원 → **총예산 초과 차단**(누적+수수료).
8. **지출 위임 중지** → 이후 요청 차단.
- 각 판정이 **감사 로그 해시 체인**에 쌓이고, 영수증에서 당시 정책 스냅샷을 보여준다.
- 시간이 모자라면 3·4를 생략하고 5→6→7→8만 보여준다.

**백업(키보드 기본 정책, 초기화 직후):** 반드시 `미등록 판매자 → 예산 초과(+수수료 5,000) → 정상` 순서. 정상 구매(82,000원)를 먼저 하면 이후 요청이 누적 예산 때문에 `budget_exceeded`까지 함께 떠서 차단 이유 설명이 흐려진다.

### 5. Kiln · Qwen3-32B 연동 (3:00–3:40)
- 자연어 정책을 **Kiln API(NPU) + Qwen3-32B**(`qwen3-32b`)로 구조화.
- 실제 호출 여부는 화면 provider 표기(`Kiln` / `Safe fallback`)로 구분. 현장 점검: `node --env-file=.env scripts/check-kiln.mjs`.
- **흐름별 토큰 사용량**을 실측 표시(통합 수치 아님). 값이 없으면 "측정 안 됨"으로 정직하게.
- Qwen은 structured output 강제가 안 되므로 **파싱·스키마 검증·사용자 확인**을 둔다.

### 6. 추론 효율 · 에너지 (3:40–4:20) ★ 차별점
- **정책은 AI가 한 번 구조화, 이후 모든 지출 판정은 코드가 한다.** 구매가 100건이어도 AI 추론은 1회.
- 화면의 `/api/energy` 카드: **줄인 AI 호출 · 줄인 토큰 · 줄인 에너지(추정) · 절감률.**
- **정직성:** 판정·호출 수는 감사 기록의 **실측**, 토큰·에너지는 **명시된 가정**(700토큰/판정, 0.3Wh/1k토큰)으로 계산한 추정치. NPU 실측 아님.
- NPU 챌린지 취지(효율적 추론)와 직결 — "불필요한 추론을 구조적으로 제거."

### 7. 온체인 증명 · 투명성 (4:20–4:50)
- 감사 해시 체인의 끝 해시를 **Sepolia 0 ETH 자기주소 거래 데이터에 기록**, 거래 해시를 영수증에 연결. (결제 자체를 온체인으로 하지는 않는다.)
- 효과는 **변경 감지**: 기록된 해시 이후 로그를 고치면 검증이 깨진다. "변조 불가능"이 아니라 "변조하면 드러난다".
- **제3자가 기록만으로** 완료된 결제가 허용 범위였는지 재구성 가능(요청 당시 정책 스냅샷 + 판정·승인 이력).
- 데모에 실제 거래 해시 + 체인 탐색기 화면 제시(현장 연결 후). RPC 점검: `node --env-file=.env scripts/check-chain.mjs <지갑주소>`.

### 8. 마무리 (4:50–5:00)
- AI 지출 방화벽 + 결제 블랙박스를 하나로.
- "AI에게 돈을 맡기되, **경계는 코드가 지키고 책임은 기록이 증명한다.**"

## Q&A 대비 — 정확히 답할 것

| 예상 질문 | 답 |
| --- | --- |
| 에너지 절감이 실측이냐? | **카운트(판정 수·AI 호출 수)는 실측, 에너지·토큰은 공개 문헌 기반 가정으로 계산한 추정.** 응답에 가정을 명시함. |
| AI가 판정을 우회할 수 있나? | 불가. 판정은 `packages/policy`의 결정론적 코드. AI는 초안만. 실행 직전 재검사도 있음. |
| Mock이냐 실제냐? | Kiln 키·지갑 있으면 실제 호출·Sepolia 거래, 없으면 Safe fallback으로 **명시 표기**. 미검증을 검증됐다 하지 않음. |
| 온체인은 왜 0 ETH 거래냐? | 결제 자체가 아니라 **감사 해시를 외부에 고정**해 이후 로그 변경을 감지하려는 용도. 해시가 맞아도 입력 내용이 현실의 사실인지까지 보증하지는 않음. |
| 정말 모든 지출을 막나? | MVP가 통제하는 건 **AgentGuard 실행 경로**. 사용자가 지갑에서 직접 보내는 송금까지 막으려면 권한을 제한하는 지갑·컨트랙트 구조가 필요(다음 단계). |
| 중지하면 거래가 취소되나? | 중지는 **아직 실행 전인 요청**과 새 요청을 막는다. 이미 전송된 거래의 취소·환불은 보장하지 않음. |
| LLM이 잘못 해석하면? | 초안은 사용자가 확인·수정 후 적용. 모호한 한도·기한은 추측하지 않고 질문으로 남김. 다만 사용자가 잘못 확정한 정책을 코드가 고쳐주지는 않음. |
| 기존 코드 vs 신규? | 대회 전 스캐폴딩·정책 엔진은 기존, 대회 중 추가분은 커밋 이력과 README에 **구분 기재**. |
| 상용화 가치? | AI 구매 에이전트를 쓰는 개인·기업의 위임 지출 감사. 고객 검증은 아직 가설 단계임을 밝힘. |
