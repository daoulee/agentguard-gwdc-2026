# AgentGuard 코드 안내서 — 비전공자용

이 문서는 AgentGuard 프로젝트의 폴더와 코드가 각각 무슨 일을 하는지 설명합니다.
코드를 처음 보는 사람도 전체 흐름을 이해할 수 있도록 **온라인 쇼핑몰과 경비실**에 비유합니다.

## 1. AgentGuard를 한 문장으로 이해하기

AgentGuard는 AI가 물건을 결제하려 할 때 먼저 규칙을 검사하는 **지출 경비실**입니다.

```text
AI의 구매 요청
   ↓
웹 화면 — 요청서를 작성하는 안내 데스크
   ↓
서버 API — 각 부서에 요청서를 전달하는 접수 직원
   ↓
정책 엔진 — 예산과 판매자를 검사하는 경비원
   ↓
자동 승인 / 사람에게 승인 요청 / 차단
   ↓
감사 로그 — 모든 과정을 적는 출입 기록부
```

현재는 실제 돈을 보내지 않는 **안전한 결제 시뮬레이션**입니다.
정책 판정, 사용자 승인·거절, 감사 기록까지 실제 프로그램 로직으로 작동합니다.

## 2. 프로젝트 전체 구조

```text
agentguard/
├── apps/
│   ├── web/                 사용자가 보는 웹 화면
│   └── server/              요청을 처리하는 API 서버
├── packages/
│   ├── shared/              모든 영역이 함께 쓰는 자료 형식과 상품 데이터
│   └── policy/              승인·대기·차단을 결정하는 정책 엔진
├── docs/                    사람을 위한 설명서
├── .env.example             필요한 비밀 설정의 빈 양식
├── package.json             프로젝트 전체 실행 명령
├── package-lock.json        설치한 도구의 정확한 버전 기록
├── tsconfig.base.json       TypeScript 공통 규칙
└── README.md                프로젝트의 첫 안내 페이지
```

비유하면 다음과 같습니다.

| 폴더 | 실제 역할 | 비유 |
|---|---|---|
| `apps/web` | 화면과 사용자 조작 | 쇼핑몰의 안내 데스크 |
| `apps/server` | HTTP 요청 처리와 임시 데이터 보관 | 요청을 접수하는 사무실 |
| `packages/policy` | 지출 정책 판정 | 출입 규칙을 검사하는 경비원 |
| `packages/shared` | 공통 타입과 상품 데이터 | 모든 직원이 쓰는 공통 서식 |
| `docs` | 개발·운영 설명 | 직원 업무 매뉴얼 |

## 3. 구매 요청 한 건이 처리되는 과정

예를 들어 사용자가 `Creator Pro Keyboard`, 98,000원을 선택한다고 가정합니다.

1. `apps/web/src/App.tsx`가 `/api/evaluate`로 구매 요청을 보냅니다.
2. `apps/server/src/index.ts`가 상품을 찾아 `PurchaseRequest` 요청서를 만듭니다.
3. 서버가 `packages/policy/src/index.ts`의 `evaluatePurchase()`에 정책과 요청서를 전달합니다.
4. 정책 엔진이 최대 예산 100,000원과 자동 승인 한도 90,000원을 검사합니다.
5. 최대 예산 안이지만 자동 승인 한도를 넘었으므로 `needs_approval`을 반환합니다.
6. 서버는 요청을 승인 대기함에 넣고 감사 로그를 기록합니다.
7. 웹 화면이 “사용자 승인 필요” 결과와 승인·거절 버튼을 보여줍니다.
8. 사용자가 승인하면 서버가 `approved` 이벤트를 감사 로그에 추가합니다.

여기서 중요한 점은 **AI가 최종 승인 여부를 마음대로 결정하지 않는다는 것**입니다.
최종 판정은 사람이 정한 숫자와 목록을 정책 엔진이 똑같은 방식으로 검사합니다.

## 4. `apps/web` — 사용자가 보는 화면

### `apps/web/index.html`

브라우저가 가장 먼저 여는 HTML 문서입니다.

- 페이지 언어가 한국어임을 알립니다.
- 모바일 화면 크기에 맞게 표시하도록 설정합니다.
- `<div id="root"></div>`라는 빈 공간을 준비합니다.
- React 프로그램의 시작 파일인 `src/main.tsx`를 불러옵니다.

**비유:** 가게를 열기 전 준비된 빈 매장입니다. 아직 상품 진열은 없지만 React가 들어올 자리가 마련되어 있습니다.

### `apps/web/src/main.tsx`

React 애플리케이션의 전원을 켜는 시작점입니다.

주요 코드 문단:

- `document.getElementById("root")`: HTML에서 React가 들어갈 자리를 찾습니다.
- `if (!root)`: 자리가 없으면 잘못된 화면이므로 즉시 오류를 냅니다.
- `createRoot(root).render(...)`: 찾은 자리에 `App` 화면을 그립니다.
- `import "./styles.css"`: 화면 디자인 규칙을 불러옵니다.

**비유:** 빈 매장의 차단기를 올리고, 진열 담당자 `App`을 매장 안으로 부르는 역할입니다.

### `apps/web/src/App.tsx`

현재 웹 화면과 사용자 동작 대부분이 들어 있는 핵심 파일입니다.

#### 상단의 문구 사전

- `navigationItems`: 상단 메뉴의 이름과 이동 위치를 정의합니다.
- `decisionCopy`: 자동 승인·승인 대기·차단일 때 보여줄 문구입니다.
- `reasonLabels`: 서버가 보내는 판정 코드를 사람이 읽을 수 있는 한국어로 바꿉니다.
- `eventLabels`: 감사 이벤트 코드를 화면용 이름으로 바꿉니다.

**비유:** 직원들이 사용하는 용어집과 안내 표지판 목록입니다.

#### 작은 화면 부품

- `ShieldMark()`: 방패 로고를 그립니다.
- `ArrowIcon()`: 버튼의 화살표를 그립니다.
- `formatKrw()`: `98000`을 `98,000원`으로 표시합니다.
- `formatTime()`: 서버 시간을 한국식 시각으로 표시합니다.

**비유:** 매장 곳곳에서 반복해서 사용하는 가격표, 시계, 아이콘 도구함입니다.

#### `requestJson()`

웹이 서버와 대화할 때 사용하는 공통 함수입니다.

- `fetch()`로 서버에 요청합니다.
- 서버가 오류를 반환하면 한국어 오류 메시지를 꺼냅니다.
- 성공하면 JSON 응답을 JavaScript 데이터로 바꿉니다.
- 내용이 없는 `204` 응답도 안전하게 처리합니다.

**비유:** 모든 요청서를 같은 규칙으로 배달하고 답장을 가져오는 사내 우편 담당자입니다.

#### `useState` 상태 묶음

화면이 현재 기억해야 하는 값을 보관합니다.

- `activeSection`: 현재 선택된 상단 메뉴
- `policy`: 서버에서 가져온 활성 정책
- `selectedProductId`: 사용자가 선택한 상품
- `fee`: 사용자가 입력한 추가 수수료
- `evaluation`: 가장 최근 정책 판정 결과
- `approvals`: 사용자 결정을 기다리는 요청 목록
- `auditEvents`: 감사 로그 목록
- `isRunning`: 정책 검사 진행 여부
- `errorMessage`: 화면에 보여줄 오류

**비유:** 안내 데스크 직원이 책상 위에 올려둔 현재 업무 메모입니다. 메모가 바뀌면 화면도 다시 그려집니다.

#### 데이터를 불러오는 코드

- `refreshActivity()`: 승인 대기함, 감사 로그, AI 토큰 사용량, 현재 정책을 새로 가져옵니다.
- 첫 번째 `useEffect`: 화면이 처음 열릴 때 정책과 활동 기록을 가져옵니다.
- 두 번째 `useEffect`: 스크롤 위치를 보고 상단 메뉴의 활성 표시를 바꿉니다.

**비유:** 개점할 때 오늘의 규칙과 업무 장부를 가져오고, 손님 위치에 따라 안내 표지판을 바꾸는 직원입니다.

#### 사용자의 행동을 처리하는 함수

- `handleNavigation()`: 메뉴를 클릭한 정확한 구역으로 부드럽게 이동합니다.
- `runEvaluation()`: 선택한 상품과 수수료를 서버의 정책 검사 API로 보냅니다.
- `resolveApproval()`: 대기 중인 요청을 승인하거나 거절합니다.
- `stopDelegation()`: 사용자의 지출 위임을 중지하고 대기 요청을 무효화합니다.
- `loadReceipt()`: 요청 당시 정책과 이후 판정을 묶은 영수증을 가져옵니다.
- `moveToSection()`: 정책 적용·거래 판정·승인 처리 후 다음 업무 화면으로 부드럽게 이동합니다.
- `showToast()`: 저장·승인·거절 결과를 화면 아래의 짧은 알림으로 전달합니다.

**비유:** 버튼을 눌렀을 때 실제 업무 담당 부서로 요청을 전달하는 창구 직원입니다.

#### 화면을 그리는 JSX 문단

`return (...)` 안은 실제 웹 페이지 구조입니다.

- `<nav>`: 상단 메뉴와 서버 작동 상태
- `#overview`: 프로젝트 설명과 현재 정책
- `.metrics`: 승인·대기·차단 개수
- `#simulator`: 상품 선택, 수수료 입력, 정책 검사 결과
- `#approvals`: 사람이 승인하거나 거절할 요청
- `#audit`: 시간순 감사 기록
- `<footer>`: 프로젝트 하단 정보

**비유:** 설계도에 따라 안내 데스크, 심사실, 승인 대기실, 기록 보관실을 배치한 것입니다.

### `apps/web/src/styles.css`

화면의 색상, 간격, 크기, 반응형 배치를 담당합니다.

주요 코드 문단:

- `:root`, `body`: 전체 글꼴과 배경색
- `.topbar`, `.nav-links`: 상단 메뉴
- `.hero`, `.policy-preview`: 첫 소개 화면과 정책 카드
- `.metrics`: 승인·대기·차단 지표
- `.simulator-*`: 거래 시뮬레이터
- `.decision-*`: 판정 결과별 초록·노랑·빨강 상태
- `.approval-*`: 승인 대기함
- `.audit-*`: 감사 로그
- `.action-toast`, `.is-resolving`: 단계 완료 알림과 승인 카드의 부드러운 진입·퇴장 효과
- `@media`: 화면이 좁을 때 모바일 형태로 재배치
- `prefers-reduced-motion`: 움직임에 민감한 사용자를 위해 애니메이션 축소

**비유:** 건물의 벽지, 가구 배치, 안내판 색상과 모바일용 접이식 배치를 정한 인테리어 설계서입니다.

### `apps/web/vite.config.ts`

웹 개발 서버와 미리보기 서버의 운영 규칙입니다.

- 개발 서버 포트는 `5173`입니다.
- `/api` 요청은 실제 API 서버 `8787`번으로 전달합니다.
- 공개 미리보기에서도 같은 API 전달 규칙을 사용합니다.
- `.trycloudflare.com` 임시 공유 주소를 허용합니다.

**비유:** 손님이 안내 데스크에 서버 업무를 물어보면 뒤쪽 사무실로 연결해 주는 내선 전화 설정입니다.

### `apps/web/package.json`

웹에 필요한 React·Vite 등의 도구와 실행 명령을 기록합니다.

- `npm run dev -w @agentguard/web`: 개발 화면 실행
- `npm run build -w @agentguard/web`: 배포용 화면 생성
- `npm run typecheck -w @agentguard/web`: 타입 오류 검사

### `apps/web/tsconfig.json`

웹 코드에 적용할 TypeScript 검사 설정입니다.
React의 JSX 문법과 Vite 환경 타입을 이해하도록 설정되어 있습니다.

## 5. `apps/server` — 요청을 처리하는 사무실

### `apps/server/src/index.ts`

브라우저의 요청을 받아 정책 엔진을 실행하고 결과를 돌려주는 API 서버입니다.

#### 서버 준비 문단

- `express()`: API 서버를 만듭니다.
- `cors()`: 허용된 다른 주소에서 API를 호출할 수 있게 합니다.
- `express.json()`: JSON 요청서를 읽을 수 있게 합니다.
- `PORT`: 기본적으로 `8787`번 창구를 사용합니다.

**비유:** 사무실 문을 열고, 접수 창구 번호와 사용할 서류 형식을 정합니다.

정책 자체와 저장 책임은 아래의 `ai.ts`, `store.ts`로 분리되어 있습니다. `index.ts`는 요청을 적절한 담당자에게 전달하는 접수 창구 역할에 집중합니다.

#### 조회 API

| 주소 | 역할 |
|---|---|
| `GET /api/health` | 서버가 살아 있는지 확인 |
| `GET /api/ai/status` | Kiln 연결 여부와 사용 모델 확인 |
| `GET /api/products` | 시뮬레이션 상품 조회 |
| `GET /api/policy` | 현재 정책 조회 |
| `GET /api/audit` | 감사 로그 조회 |
| `GET /api/approvals` | 승인 대기 목록 조회 |

#### 정책 API

- `POST /api/policies/interpret`: 자연어를 정책 초안으로 변환
- `POST /api/policies`: 사용자가 검토한 초안을 실제 정책으로 적용

정책을 새로 적용하면 이전 정책으로 만들어진 승인 대기 요청은 안전하게 종료되고 감사 로그에 이유가 남습니다.

#### `POST /api/evaluate`

정책 판정의 중심 API입니다.

1. 상품 ID와 수수료를 받습니다.
2. 실제 목업 상품이 있는지 검사합니다.
3. 수수료가 올바른 숫자인지 검사합니다.
4. 표준 `PurchaseRequest` 요청서를 만듭니다.
5. `evaluatePurchase()` 정책 엔진을 실행합니다.
6. 결과에 따라 승인·차단·승인 대기를 기록합니다.
7. 판정 결과를 웹으로 돌려줍니다.

**비유:** 접수 직원이 신청서의 기본 오류를 확인한 다음 경비원에게 넘기고, 결과에 맞는 대기실로 안내합니다.

#### `POST /api/approvals/:requestId`

대기 중인 요청을 사람이 승인하거나 거절할 때 호출합니다.
이미 처리됐거나 존재하지 않는 요청을 다시 처리하지 못하게 막습니다.

#### `POST /api/policy/stop`

현재 지출 위임을 중지하고 대기 중인 승인 요청을 무효화합니다. 중지 사실은 감사 로그에 남습니다.

#### `GET /api/receipts/:requestId`

요청 당시 정책 스냅샷과 판정·승인 기록을 영수증으로 돌려줍니다.

#### `GET /api/audit/anchor-payload`와 `POST /api/audit/anchors`

첫 API는 현재 감사 해시를 Sepolia 거래 데이터로 만드는 데 필요한 값을 돌려줍니다. 브라우저 지갑이 거래를 제출한 뒤 두 번째 API가 테스트넷 RPC의 거래·영수증을 검사하고 검증된 거래 해시만 감사 로그에 연결합니다. 실제 거래 실행에는 Sepolia RPC와 사용자 지갑이 필요합니다.

### `apps/server/src/ai.ts`

자연어 정책 변환 방식을 선택하는 AI 어댑터입니다.

- Kiln URL과 키가 설정되어 있으면 공식 Challenge B의 `Qwen3-32B` 모델에 JSON 출력을 요청합니다.
- AI가 만든 판매자와 카테고리는 현재 상품 목록과 대조합니다.
- 문장에 없는 자동 승인 한도나 기한은 지어내지 않고 `missingFields`와 확인 질문으로 표시합니다.
- 8초 안에 응답하지 않거나 JSON이 잘못되면 안전 규칙 변환기로 전환합니다.
- API 키 자체는 브라우저에 전달하지 않습니다.

**비유:** 통역사가 근무 중이면 자연어를 규칙 서식으로 번역하고, 통역사가 자리를 비우거나 번역이 불분명하면 검증된 기본 서식 담당자가 대신 처리합니다.

### `apps/server/src/store.ts`

현재 정책, 승인 대기함, 감사 로그를 `apps/server/data/state.json`에 저장합니다.

- 임시 파일에 먼저 쓴 뒤 이름을 교체해 저장 도중 파일이 깨질 가능성을 줄입니다.
- 각 감사 이벤트에 이전 이벤트 해시와 현재 SHA-256 해시를 기록합니다.
- 조회할 때 해시 체인을 다시 계산해 중간 기록의 변조 여부를 확인합니다.
- `state.json`은 실행 데이터라 Git에 커밋하지 않습니다.

**비유:** 서버를 꺼도 남는 장부이며, 각 페이지에 이전 페이지의 봉인 번호를 적어 중간 페이지를 몰래 바꾸기 어렵게 만든 구조입니다.

### `apps/server/package.json`

서버에 필요한 Express, 정책 엔진, 공통 타입 등의 도구와 명령을 정의합니다.

### `apps/server/tsconfig.json`

서버 코드를 검사하고 실행용 JavaScript를 `dist` 폴더에 만들도록 설정합니다.

## 6. `packages/policy` — 규칙을 검사하는 경비원

### `packages/policy/src/index.ts`

`evaluatePurchase(policy, request)`가 최종 지출 판정을 담당하고, `createFallbackPolicyDraft()`가 AI를 사용할 수 없을 때 자연어에서 안전한 정책 초안을 만듭니다.

검사 순서:

1. 요청 시간이 정책 기한을 넘었는지 검사
2. 상품 가격과 수수료의 합이 최대 예산을 넘는지 검사
3. 판매자가 허용 목록에 있는지 검사
4. 상품 카테고리가 허용 목록에 있는지 검사
5. 위반이 하나라도 있으면 `block`
6. 위반은 없지만 자동 승인 한도를 넘으면 `needs_approval`
7. 모든 조건을 충족하면 `allow`

**비유:** 출입증, 방문 시간, 방문 목적을 순서대로 확인하는 경비원입니다. 말투나 기분에 따라 결과를 바꾸지 않고 같은 입력에는 같은 규칙을 적용합니다.

AI 모델은 자연어를 정책 초안으로 바꾸지만, 돈을 막는 마지막 규칙은 항상 이 코드가 담당합니다.

### `packages/policy/src/index.test.ts`

정책 엔진이 바뀌어도 중요한 규칙이 망가지지 않았는지 자동으로 확인합니다.

- 82,000원 정상 거래 → 자동 승인
- 98,000원 거래 → 사용자 승인 요청
- 미등록 판매자 → 차단
- 98,000원 + 수수료 5,000원 → 예산 초과 차단
- 한국어 문장에서 10만원 예산과 9만원 승인 한도 추출
- `8만 5천원`처럼 결합된 금액 해석
- 게이밍 모니터 요청을 모니터 카테고리와 등록 판매자에 연결하고 누락된 조건은 질문으로 남기는지 검사

**비유:** 경비원이 업무 매뉴얼대로 판정하는지 매일 시행하는 모의 훈련입니다.

## 7. `packages/shared` — 모두가 쓰는 공통 서식

### `packages/shared/src/index.ts`

웹, 서버, 정책 엔진이 같은 뜻으로 데이터를 주고받도록 타입을 정의합니다.

주요 타입:

| 타입 | 의미 | 비유 |
|---|---|---|
| `SpendingPolicy` | 예산·판매자·기한 등 지출 규칙 | 경비실 업무 규정 |
| `PolicyDraft` | AI가 만들고 사용자가 검토할 정책 초안 | 결재 전 규정 초안 |
| `Product` | 상품 정보 | 상품표 |
| `PurchaseRequest` | AI가 보낸 구매 요청 | 결제 신청서 |
| `PolicyDecision` | 승인·대기·차단 결과 | 심사 결과표 |
| `PurchaseEvaluation` | 상품·요청·판정을 묶은 결과 | 신청서 전체 철 |
| `AuditEvent` | 시간순 처리 기록 | 출입 기록 한 줄 |
| `HealthResponse` | 서버 상태 응답 | 사무실 정상 운영 표시 |

`mockProducts`는 키보드와 게이밍 모니터 정책에 사용하는 가상 상품입니다. 각 카테고리에는 자동 승인·사용자 승인·차단을 보여주는 세 가지 시나리오가 있습니다. `merchantDirectory`는 등록 판매자와 취급 카테고리를 나타내는 작은 카탈로그입니다.

공통 타입을 먼저 수정해야 웹과 서버가 서로 다른 형태의 서류를 사용하는 사고를 막을 수 있습니다.

## 8. 루트 설정 파일

### `package.json`

프로젝트 전체의 대표 리모컨입니다.

- `npm run dev`: 웹과 서버를 동시에 개발 모드로 실행
- `npm test`: 모든 자동 테스트 실행
- `npm run typecheck`: 모든 TypeScript 타입 검사
- `npm run build`: 모든 배포용 파일 생성

`workspaces`는 `apps/*`와 `packages/*`를 한 프로젝트처럼 연결합니다.

### `package-lock.json`

설치된 라이브러리의 정확한 버전과 출처를 자동으로 기록합니다.
직접 편집하지 말고 `npm install`이 관리하도록 둡니다.

**비유:** 같은 재료를 다시 주문할 수 있도록 제조사와 제품 번호까지 적어 둔 납품 명세서입니다.

### `tsconfig.base.json`

모든 TypeScript 코드가 함께 지킬 공통 검사 규칙입니다.
`strict: true`는 애매하거나 위험한 코드를 더 일찍 발견하도록 검사 강도를 높입니다.

### `.env.example`

실행에 필요한 환경 변수의 **이름만** 보여주는 견본입니다.

- `PORT`: API 서버 포트
- `KILN_*`: 향후 FuriosaAI/Kiln 모델 연결 설정
- `RPC_URL`, `CHAIN_ID`, `AUDIT_CONTRACT_ADDRESS`: 향후 테스트넷 연결 설정

실제 API 키는 `.env`에만 넣고 Git에 커밋하지 않습니다.

**비유:** 금고 비밀번호 자체가 아니라 “이 칸에 금고 비밀번호를 적으세요”라고 표시된 빈 양식입니다.

### `.gitignore`

API 키, 설치 결과, 빌드 결과처럼 Git에 올리면 안 되거나 다시 만들 수 있는 파일을 제외합니다.

### `README.md`

처음 프로젝트를 받은 팀원이 목적, 구조, 실행 방법을 확인하는 첫 페이지입니다.

## 9. 자동 생성되어 직접 수정하지 않는 것

| 이름 | 설명 |
|---|---|
| `node_modules/` | `npm install`이 내려받은 라이브러리 |
| `dist/` | `npm run build`가 만든 배포용 결과물 |
| `*.tsbuildinfo` | TypeScript가 빠른 재검사를 위해 만든 캐시 |

이 파일들은 원본 코드가 아닙니다. 삭제되어도 설치나 빌드 명령으로 다시 생성할 수 있습니다.

## 10. 기능을 바꾸고 싶을 때 어디를 수정할까?

| 하고 싶은 일 | 먼저 볼 파일 |
|---|---|
| 화면 문구·버튼·구역 변경 | `apps/web/src/App.tsx` |
| 색상·간격·모바일 디자인 변경 | `apps/web/src/styles.css` |
| 새로운 API 추가 | `apps/server/src/index.ts` |
| 승인·차단 조건 변경 | `packages/policy/src/index.ts` |
| 정책 엔진 오류 방지 테스트 추가 | `packages/policy/src/index.test.ts` |
| 데이터 항목 추가·변경 | `packages/shared/src/index.ts` |
| 실행 명령이나 라이브러리 변경 | 해당 폴더의 `package.json` |
| API 키 이름 추가 | `.env.example`와 개인 `.env` |

## 11. 안전하게 수정하는 순서

```bash
# 1. 개발 서버 실행
npm run dev

# 2. 코드를 수정한 뒤 자동 테스트
npm test

# 3. 웹·서버가 같은 데이터 형식을 쓰는지 검사
npm run typecheck

# 4. 실제 배포 파일이 만들어지는지 검사
npm run build
```

API 응답의 모양을 바꾸려면 다음 순서가 안전합니다.

1. `packages/shared`의 공통 타입을 먼저 변경합니다.
2. `packages/policy` 또는 `apps/server`에서 새 타입을 사용합니다.
3. `apps/web`에서 새 응답을 화면에 표시합니다.
4. 테스트, 타입 검사, 빌드를 모두 실행합니다.

## 12. 현재 구현과 앞으로 구현할 부분

### 현재 구현됨

- 자연어 정책 작성과 편집·적용
- 상품·판매자 카탈로그에 근거한 의도 보정
- 누락 조건 확인 질문과 확인 전 정책 적용 방지
- Kiln `Qwen3-32B` 연결 어댑터와 실패 시 안전 폴백
- 누적 예산과 위임 중지, 정책 스냅샷 영수증
- 정책·승인 대기·감사 로그의 로컬 영구 저장
- 코드 기반 정책 판정
- 자동 승인·사용자 승인 대기·즉시 차단
- 사용자 승인과 거절
- SHA-256 해시 체인 감사 로그와 무결성 검증
- 카테고리별 세 가지 상품 시뮬레이션
- 정책 엔진·한국어 금액 변환 자동 테스트
- 반응형 웹 화면

### 아직 시뮬레이션 또는 미구현

- 운영용 데이터베이스와 다중 사용자 데이터 분리
- 사용자 로그인과 관리자 권한
- 실제 결제 수단 연결
- 블록체인 테스트넷 감사 해시 기록
- 운영 환경용 보안과 모니터링

따라서 지금 AgentGuard는 **핵심 아이디어와 사용자 흐름을 증명하는 작동형 MVP**입니다.
실제 금융 서비스로 배포하려면 인증, 영구 저장소, 권한 관리, 보안 검토가 추가로 필요합니다.
